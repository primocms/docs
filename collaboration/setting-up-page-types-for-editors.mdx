Use page types to choose what editors can change: page fields, section content, and the blocks they can add to the body. You need developer access to configure them.

## Choose a fixed or flexible layout

Start with the editor's task. A profile may need the same layout every time; an About page may need sections editors can arrange.

| Editors need to… | Configure the page type with… |
| --- | --- |
| Fill in content without changing the body layout | Starting body sections and an empty available-block list |
| Add sections and change their order | A focused list of available blocks, with optional starting body sections |
| Keep navigation and footer structure consistent | Shared header and footer sections |

Editors can edit the fields in shared sections. Use Site Field references when the same content should appear across different page types.

## Configure editing options

<Steps>
  <Step title="Open the page type">
    Choose **Pages → Manage page types** and open the type you want to configure.
  </Step>
  <Step title="Set the starting layout">
    Place shared blocks in the header and footer. Add body sections to give new pages a useful starting layout.

    Header and footer sections stay shared. Body sections are copied when a page is created; later template changes do not replace them on existing pages.
  </Step>
  <Step title="Choose available blocks">
    In the **Blocks** tab, enable only the blocks editors need to add. For a flexible article layout, you might build or import Text, Image, and Quote blocks. Leave the list empty if editors should only fill in the existing layout.
  </Step>
  <Step title="Add page fields">
    Define content each page needs, such as a title or biography. Give fields clear labels and use Info fields for instructions.

    To display a page field in a block, add a **Page Field** reference to that block. For search metadata, add the appropriate tags to the page type's [Head HTML](/reference/site-configuration#page-metadata).
  </Step>
  <Step title="Test as a content editor">
    Create a page with realistic content, then sign in as an editor. Check that the fields and layout controls support the task. Test a second page to verify shared content and independent body content.
  </Step>
</Steps>

## Example page types you can create

These are suggested designs, not built-in presets. Create or import the blocks they use and define the fields yourself. Pages with similar needs can share one page type.

| Example type | Possible page fields | Possible body setup |
| --- | --- | --- |
| Blog Post | `title` (Text), `body` (Rich Text), `publish_date` (Date) | Fixed Post Content section connected to the page fields |
| Team Member | `name` (Text), `photo` (Image), `bio` (Rich Text) | Fixed Profile section connected to the page fields |
| Event | `title` (Text), `date` (Date), `location` (Text), `registration_link` (Link) | Event Details section, with optional Text and Image blocks |
| General Page | `meta_title` and `meta_description` (Text) | Flexible body using selected Hero, Text, and Image blocks |

See [Build a blog for content editors](/collaboration/example-blog) for a complete example.

A Date field records a date; it does not schedule publishing. A Link field stores a destination; registration or newsletter processing requires your own service. Fields such as `featured` or `status` only affect the rendered page if your code uses them.

## Make fields easy to use

Use labels that explain the content, such as **Featured image** instead of **Image 1**. Add an Info field for image dimensions, writing guidance, or where a value appears. Instructions guide editors; they do not enforce required fields or text-length limits.

For example, if your block displays `featured_image` at the top of a post, add an Info field saying: "Choose a landscape image for the post header and add descriptive alt text." Only describe social-sharing behavior if you have also connected the field to social metadata tags.

## Add optional editing patterns

<AccordionGroup>
  <Accordion title="Show fields only when relevant">
    For an Event type you create, add `event_type` as Select with In Person and Virtual options. Put `venue` after it and set a condition to show Venue for In Person. Add `meeting_link` as URL and show it for Virtual.

    Conditions control the form. Add matching conditions in your block code if the published page should also hide those values. See [Conditional fields](/building-sites/working-with-fields#conditional-fields).
  </Accordion>
  <Accordion title="List pages of one type">
    Build a Team Grid block and give it a Page List field named `members`, configured for your Team Member type. The field supplies all pages of that type; your block code renders the list.

    For a hand-picked list, use a Repeater containing a Page field. See [Field types](/reference/field-types).
  </Accordion>
</AccordionGroup>

## Adjust the setup after handoff

Ask editors which blocks they need, which fields confuse them, and where they work around the layout. Make a test page before changing the shared setup, then check both new and existing pages.

| Problem | Change to consider |
| --- | --- |
| Editors cannot add a block | Enable it in the page type; for a fixed layout, decide whether to allow body changes |
| Too many similar choices | Keep one useful block and expose a Select field for variations you implement |
| Pages look inconsistent | Use a fixed body or reduce the available-block list |
| Editors misunderstand a field | Improve its label or add an Info field with a concrete example |

Tell editors what changed and show them how to use it. Agree on review before publishing as a team process; the page type does not create an approval workflow.

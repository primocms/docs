This guide covers deploying Primo to production. Choose the deployment method that matches your needs and technical expertise.

<Warning>
  **Persistent Storage Required**: Primo stores all data in a SQLite database and needs persistent disk storage to function. Traditional serverless platforms (Vercel, Netlify, Cloudflare Pages) have ephemeral file systems and won't work.
</Warning>

## Quick Deploy: Railway

The fastest way to deploy Primo to production.

### Prerequisites

- [Railway account](https://railway.com/?referralCode=RCPU7k); review [plan and resource pricing](https://docs.railway.com/pricing/plans)
- Domain name (optional, Railway provides a free subdomain)

### Deployment Steps

<Steps>
  <Step title="Click deploy button">
    <Frame>
      <a href="https://railway.com/deploy/palacms?referralCode=RCPU7k">
        <img src="https://railway.com/button.svg" alt="Deploy Primo on Railway" />
      </a>
    </Frame>
  </Step>

  <Step title="Configure environment (optional)">
    Set environment variables if you want automated setup:
    - `PRIMO_SUPERUSER_EMAIL`
    - `PRIMO_SUPERUSER_PASSWORD`
    - `PRIMO_USER_EMAIL` and `PRIMO_USER_PASSWORD`: create the regular Developer account used for Primo sign-in
    - `PRIMO_APP_URL`: set the public HTTPS URL used for backend links
    - `PRIMO_DOMAIN_PROVIDER=railway` and `PRIMO_RAILWAY_TOKEN`: connect custom site domains from the Primo dashboard (see below). Leave these unset when you only use the Railway-generated hostname
  </Step>

  <Step title="Wait for deployment">
    Railway will:
    - Pull the Docker image
    - Create a persistent volume
    - Deploy the container
    - Generate a URL
  </Step>

  <Step title="Access your instance">
    Click the generated URL to access Primo. If you did not create a superuser through environment variables, complete the setup screen. If you did, sign in to Primo with the regular account created by `PRIMO_USER_EMAIL` and `PRIMO_USER_PASSWORD`; the superuser account is for PocketBase at `/_/`.
  </Step>

  <Step title="Connect site domains from the dashboard">
    To connect domains to sites without leaving the Primo dashboard, give Primo access to your Railway service:

    1. In your Railway project, go to **Settings → Tokens → New Project Token**
    2. Add two variables to the service, then redeploy:
       - `PRIMO_DOMAIN_PROVIDER` = `railway`
       - `PRIMO_RAILWAY_TOKEN` = the token
    3. In the Primo dashboard, open a site's menu and choose **Assign domain**. Primo attaches the domain to your Railway deployment, shows the DNS records to add at your registrar, and marks the site live once the certificate is issued.

    Without these variables, connect the domain by hand:

    1. In your Railway service, go to **Settings → Networking → Custom Domain** and add the domain.
    2. Add the DNS records Railway shows at your registrar, and wait for Railway to issue the certificate.
    3. In the Primo dashboard, choose **Assign domain** on the site, enter the domain, and click **Mark as connected**.
  </Step>
</Steps>

Verify the volume mounts at `/app/pb_data` before creating content. See [Railway volumes](https://docs.railway.com/volumes) for the host controls.

**Cost**: Check [Railway plan and resource pricing](https://docs.railway.com/pricing/plans). Compute, volume storage, and bandwidth contribute to usage.

<Tip>
  Railway manages the infrastructure and certificates. You still configure domains, backups, and access for your Primo instance.
</Tip>

## VPS Deployment

Deploy to any VPS for full control over your infrastructure.

### Prerequisites

- VPS with Docker installed ([Hetzner](https://www.hetzner.com), [DigitalOcean](https://www.digitalocean.com), etc.)
- SSH access to your server
- Domain name pointed to your server IP
- Basic command line knowledge

### Option 1: Docker Compose (Recommended)

<Steps>
  <Step title="SSH into your server">
    ```bash
    ssh user@your-server-ip
    ```
  </Step>

  <Step title="Create project directory">
    ```bash
    mkdir primo
    cd primo
    ```
  </Step>

  <Step title="Create docker-compose.yml">
    ```yaml
    services:
      primo:
        image: ghcr.io/primocms/primo:latest
        restart: always
        ports:
          - "127.0.0.1:8080:8080"
        volumes:
          - primo-data:/app/pb_data
        environment:
          - PRIMO_APP_URL=https://your-domain.com
          # Optional: automated setup
          # - PRIMO_SUPERUSER_EMAIL=admin@example.com
          # - PRIMO_SUPERUSER_PASSWORD=${SUPERUSER_PASSWORD:?Set SUPERUSER_PASSWORD}
          # - PRIMO_USER_EMAIL=developer@example.com
          # - PRIMO_USER_PASSWORD=${USER_PASSWORD:?Set USER_PASSWORD}

    volumes:
      primo-data:
    ```
  </Step>

  <Step title="Start the container">
    Leave the account variables commented out for browser setup. For automated setup, enable both account pairs and set distinct generated passwords in a private `.env` file before starting.

    ```bash
    docker compose up -d
    ```
  </Step>

  <Step title="Verify it's running">
    ```bash
    docker compose logs -f
    ```
    You should see logs indicating the server started on port 8080.
  </Step>
</Steps>

### Option 2: Docker Run

For simpler setups without compose:

```bash
docker run -d \
  --name primo \
  --restart always \
  -p 127.0.0.1:8080:8080 \
  -v primo-data:/app/pb_data \
  -e PRIMO_APP_URL=https://your-domain.com \
  ghcr.io/primocms/primo:latest
```

### Configure Reverse Proxy

The VPS examples bind port 8080 to the server's loopback address. Run the reverse proxy on that host and expose ports 80 and 443 for public traffic. Replace `your-domain.com` with a hostname whose DNS points to the VPS.

<Tabs>
  <Tab title="Nginx">
    Install Nginx and Certbot for your operating system using the [Certbot instructions](https://certbot.eff.org/instructions?ws=nginx). On a typical Linux installation, save this initial HTTP configuration as `/etc/nginx/conf.d/primo.conf`:

    ```nginx primo.conf
    server {
        listen 80;
        server_name your-domain.com;
        client_max_body_size 32m;

        location / {
            proxy_pass http://127.0.0.1:8080;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_buffering off;
            proxy_read_timeout 360s;
            proxy_set_header Host $http_host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    Test and reload Nginx, then verify the hostname reaches the instance over HTTP. Complete account setup after HTTPS is enabled.

    ```bash
    sudo nginx -t
    sudo systemctl reload nginx
    curl -I http://your-domain.com/admin/
    ```

    Obtain a certificate and let Certbot add HTTPS and the HTTP redirect:

    ```bash
    sudo certbot --nginx --redirect -d your-domain.com
    sudo nginx -t
    sudo certbot renew --dry-run
    ```

    Open `https://your-domain.com/admin/` and verify the certificate before signing in. This sequence starts without certificate paths; Certbot adds them after issuance.
  </Tab>

  <Tab title="Caddy">
    Caddy automatically handles SSL certificates:

    ```caddy
    your-domain.com {
        reverse_proxy localhost:8080
    }
    ```

    Start Caddy:
    ```bash
    caddy run --config Caddyfile
    ```
  </Tab>

  <Tab title="Traefik">
    Use an existing Traefik installation with its Docker provider, a `websecure` entry point, and a `letsencrypt` certificate resolver configured. Put Traefik and Primo on the same Docker network. Merge these labels into the Primo service from the Compose example:

    ```yaml
    services:
      primo:
        image: ghcr.io/primocms/primo:latest
        labels:
          - "traefik.enable=true"
          - "traefik.http.routers.primo.rule=Host(`your-domain.com`)"
          - "traefik.http.routers.primo.entrypoints=websecure"
          - "traefik.http.routers.primo.tls.certresolver=letsencrypt"
          - "traefik.http.services.primo.loadbalancer.server.port=8080"
    ```
  </Tab>
</Tabs>

## Platform-Specific Guides

### Hetzner Cloud

[Hetzner](https://www.hetzner.com) offers affordable VPS hosting in Europe and the US.

1. Choose a current VPS plan with enough memory and persistent storage for your sites
2. Install Docker:
   ```bash
   curl -fsSL https://get.docker.com -o get-docker.sh
   sudo sh get-docker.sh
   ```
3. Follow VPS deployment steps above
4. Configure firewall to allow ports 80, 443, and 22

### DigitalOcean

[DigitalOcean](https://www.digitalocean.com) provides simple VPS hosting with excellent documentation.

1. Choose a current Droplet plan with persistent storage
2. Choose "Docker" from one-click apps (or install manually)
3. Follow VPS deployment steps above
4. Use DigitalOcean's cloud firewalls for security

### Fly.io

[Fly.io](https://fly.io) bills compute and persistent volumes by usage. New accounts have a trial, not an ongoing free tier; check [Fly.io pricing](https://fly.io/docs/about/pricing/). Use one Machine for this single-volume SQLite deployment:

<Steps>
  <Step title="Install Fly CLI">
    ```bash
    curl -L https://fly.io/install.sh | sh
    ```
  </Step>

  <Step title="Login to Fly">
    ```bash
    fly auth login
    ```
  </Step>

  <Step title="Create fly.toml">
    ```toml
    app = "your-app-name"
    primary_region = "sjc"

    [build]
      image = "ghcr.io/primocms/primo:latest"

    [http_service]
      internal_port = 8080
      force_https = true

    [[mounts]]
      source = "primo_data"
      destination = "/app/pb_data"

    [env]
      PRIMO_APP_URL = "https://your-app-name.fly.dev"
    ```
  </Step>

  <Step title="Create volume">
    ```bash
    fly apps create your-app-name
    fly volumes create primo_data --app your-app-name --region sjc --size 3
    ```
  </Step>

  <Step title="Deploy">
    ```bash
    fly deploy --app your-app-name --ha=false
    ```
  </Step>
</Steps>

## Database Backups

Primo uses SQLite, stored in `/app/pb_data`. Back up this directory regularly.

<Note>
Backups stored on the same volume do not protect against losing that volume. Keep an off-site copy and separately back up uploads stored in S3; PocketBase backups exclude S3-uploaded files.
</Note>

### PocketBase Automated Backups (Recommended)

PocketBase has built-in automated backups that you can configure through the admin UI.

New instances back up daily at 03:00 and keep the 7 most recent backups, stored locally. To use a different schedule from the start, set [`PRIMO_BACKUP_CRON`](/reference/environment-variables#primo_backup_cron). To change it later, or add off-site storage, use the admin UI:

<Steps>
  <Step title="Access PocketBase Admin">
    Navigate to `https://your-domain.com/_/` and sign in with your PocketBase superuser credentials.
  </Step>

  <Step title="Go to Settings → Backups">
    Click on Settings in the sidebar, then select the Backups tab.
  </Step>

  <Step title="Configure backup schedule">
    Set a cron expression for your backup schedule:
    - **Daily at 2 AM**: `0 2 * * *`
    - **Every 6 hours**: `0 */6 * * *`
    - **Hourly**: `0 * * * *`
    - **Every minute** (not recommended): `* * * * *`
  </Step>

  <Step title="Choose backup location">
    - **Local storage**: Backups saved to `/app/pb_data/backups`
    - **S3-compatible storage**: Configure [AWS S3](https://aws.amazon.com/s3/), [Backblaze B2](https://www.backblaze.com/b2/cloud-storage.html), or similar for off-site backups
  </Step>

  <Step title="Set retention policy">
    Configure how many backup files to keep. For example, retaining 7 files gives you about 7 days of history with one successful daily backup.
  </Step>
</Steps>

<Tip>
For production sites, configure S3-compatible storage for off-site backups. This protects against server failures.
</Tip>

### Manual backups with Docker

Prefer PocketBase's built-in backups for a running instance. A raw copy of `pb_data` must be made while Primo is stopped to keep SQLite and its associated files consistent. See [PocketBase backup and restore](https://pocketbase.io/docs/going-to-production/#backup-and-restore).

For the container named `primo` created with the Docker Run example:

```bash backup-primo.sh
#!/usr/bin/env bash
set -euo pipefail

task_backup_path="./backups/pb_data_$(date +%Y%m%d_%H%M%S)"
mkdir -p ./backups
docker inspect --format '{{.Image}}' primo > "${task_backup_path}.image"
docker stop primo
trap 'docker start primo >/dev/null' EXIT
docker cp primo:/app/pb_data "$task_backup_path"
printf 'Backup saved to %s\n' "$task_backup_path"
```

This briefly stops the site. Run the script on the Docker host and copy the backup and image record off-server. For Compose, use `docker compose stop primo`, get its container ID with `docker compose ps -aq primo`, copy from that ID, and restart with `docker compose start primo`. Do not use `docker compose down` before copying: it removes the container.

### Restore from a backup

For a PocketBase backup ZIP, use **Settings → Backups → Restore** in `/_/`. Test on an isolated instance before restoring production.

For a raw `pb_data` directory made with the script above, restore into a **new** named volume and container. Keep the existing instance and backup until you verify the restored site. Set `task_backup_path` to your actual backup folder; the recorded image must still exist on the Docker host, or you must pull the same version from the registry.

```bash
set -euo pipefail
task_backup_path=./backups/pb_data_20261011_020000
task_restore_image=$(cat "${task_backup_path}.image")
test -f "$task_backup_path/data.db"

docker create --name primo-restored \
  -p 127.0.0.1:8081:8080 \
  -v primo-restored-data:/app/pb_data \
  "$task_restore_image"
docker cp "$task_backup_path/." primo-restored:/app/pb_data
docker start primo-restored
```

Use a new container and volume name for each restore attempt. Open `http://localhost:8081/admin/` on the Docker host and check sign-in, pages, content, and uploads before switching your reverse proxy. Hostname routing may require a matching Host header or a temporary domain assignment in the isolated copy. Restore separately stored S3 media too. [Docker supports copying into a stopped container](https://docs.docker.com/reference/cli/docker/container/cp/).

<Warning>
Restoring replaces the site's state with the backup's state. Keep a backup of the current instance and verify the restore before routing production traffic to it.
</Warning>

## Updating Primo

### Docker Compose

```bash
# Pull latest image
docker compose pull

# Restart with new image
docker compose up -d
```

### Docker Run

```bash
# Stop and remove old container
docker stop primo
docker rm primo

# Pull latest image
docker pull ghcr.io/primocms/primo:latest

# Start new container (same command as initial deploy)
docker run -d \
  --name primo \
  --restart always \
  -p 127.0.0.1:8080:8080 \
  -v primo-data:/app/pb_data \
  -e PRIMO_APP_URL=https://your-domain.com \
  ghcr.io/primocms/primo:latest
```

Keep the original environment variables and volume when recreating the container.

<Tip>
Always backup before updating, especially for major version changes.
</Tip>

## Performance Optimization

### Enable Gzip Compression

In your reverse proxy:

**Nginx:**
```nginx
gzip on;
gzip_types text/plain text/css application/json application/javascript text/xml application/xml text/javascript;
```

**Caddy:**
```caddy
encode gzip
```

### Cache published assets carefully

Keep `/admin`, `/api`, and authentication traffic out of CDN caches. Use long-lived immutable caching only for assets whose URLs change when their contents change. Fixed image names, HTML, and unversioned scripts need revalidation or short cache lifetimes.

For a reverse proxy, keep asset requests routed to Primo and verify the response headers after publishing. A new Nginx `location` block without `proxy_pass` would try to serve files from Nginx's own filesystem.

### Use a CDN

Point your domain through Cloudflare (free tier) for:
- Global CDN
- DDoS protection
- SSL certificates
- Caching

## Security Checklist

<AccordionGroup>
  <Accordion title="Use strong passwords">
    Generate random passwords for all accounts. Never use default or simple passwords.
  </Accordion>

  <Accordion title="Enable firewall">
    Only allow ports 80, 443, and 22 (SSH). Block all other inbound traffic.
  </Accordion>

  <Accordion title="Keep Docker updated">
    Regularly update Docker and the Primo image for security patches.
  </Accordion>

  <Accordion title="Use HTTPS everywhere">
    Never serve Primo over HTTP in production. Use Let's Encrypt for free SSL certificates.
  </Accordion>

  <Accordion title="Restrict SSH access">
    - Disable password authentication
    - Use SSH keys only
    - Change default SSH port
    - Use fail2ban to block brute force attempts
  </Accordion>

  <Accordion title="Regular backups">
    Automate daily backups and store them off-server (S3, Backblaze, etc.).
  </Accordion>

  <Accordion title="Monitor logs">
    Check Docker logs regularly for suspicious activity:
    ```bash
    docker compose logs -f --tail=100
    ```
  </Accordion>
</AccordionGroup>

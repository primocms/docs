---
title: 'Local Development'
description: 'Run the Primo CMS locally with primo dev and sync changes between files and the editor.'
---

`primo dev` runs the full Primo CMS on your machine and keeps it in sync with your local files. You write blocks and content in your editor; the CMS picks up the changes. With `--author cms`, edits you make in the CMS are written back to disk instead (see [Author Modes](#author-modes)).

## Starting the Dev Server

From a workspace root (the directory containing `server.yaml`):

```bash
primo dev
```

`primo dev` runs until you stop it (Ctrl+C). It prints the URLs for each site:

- `http://127.0.0.1:3000/admin/dashboard` — the dashboard
- `http://my-site.localhost:3000/admin/site` — the CMS editor for a site
- `http://my-site.localhost:3000/` — the site's preview

Run from the folder that *contains* a workspace, `primo dev` tells you to `cd` into it rather than creating a new one.

<Tip>
From scripts or AI agents, run `primo dev` in the background, log to a file, and stop it by its PID when you're done:

```bash
primo dev > dev.log 2>&1 &
```
</Tip>

### Ports

`primo dev` uses two ports: the CMS port (3000 by default, or `port:` in `server.yaml`) and the next one up for live reload. If either is taken, it picks the next free pair and tells you:

```
ℹ Port 3000 or reload port 3001 is in use. Using http://localhost:3002 for this session.
```

Local site hosts like `my-site.localhost:3000` are updated to the port in use, so you can run several workspaces side by side.

### Leftover CMS processes

If a previous `primo dev` was killed without shutting down its CMS, the next start tells you which process is in the way:

```
✖ Failed to start: A Primo CMS from an earlier session is still running on port 3002 (pid 8087); the command that started it exited without stopping it. Stop it with `kill 8087`, or run `primo dev --force` to stop it and start fresh.
```

<Warning>
`primo dev --force` stops **any** process on the workspace's port, including a `primo dev` running for a different workspace. Prefer `kill <pid>` when you have more than one workspace running.
</Warning>

### Options

```bash
primo dev -p 8080            # Use a custom port
primo dev --force            # Stop whatever holds the port, then start
primo dev --author files     # Default: files are source of truth
primo dev --author cms       # CMS is source of truth
primo dev --author both      # Bidirectional (beta)
```

## Author Modes

`--author` controls which side wins when files and the CMS disagree. This is the most important concept in local dev — pick a mode that matches how you're working.

<Tabs>
  <Tab title="files (default)">
    **Files are source of truth.**

    - Edits to local files are imported into the CMS on save.
    - The CMS UI is **read-only** for content that's tracked in files — you'll see a banner.
    - Use this mode when you're building blocks or page types in your editor.

    ```bash
    primo dev --author files
    ```
  </Tab>

  <Tab title="cms">
    **CMS is source of truth.**

    - Edits in the CMS are written to local files.
    - Edits to local files get reverted on the next CMS write.
    - Use this mode when you want to do most of your work in the browser editor and just want files for Git history.

    ```bash
    primo dev --author cms
    ```
  </Tab>

  <Tab title="both (beta)">
    **Bidirectional sync.**

    - Both sides can write.
    - On conflict, CMS edits are often lost in favor of file edits — treat this as preview-quality.

    ```bash
    primo dev --author both
    ```
  </Tab>
</Tabs>

## Site Layout

Each site folder follows this layout:

```
sites/my-site/
├── site.yaml          # Site name, id, group
├── site/
│   ├── fields.yaml    # Site-wide fields (logo, nav, etc.)
│   ├── content.yaml   # Values for site fields
│   ├── head.svelte    # Custom <head> content
│   └── foot.svelte    # Custom end-of-body content
├── blocks/
│   └── hero/
│       ├── component.svelte
│       ├── fields.yaml
│       └── content.yaml
├── page-types/
│   └── blog-post/
│       └── config.yaml
├── pages/
│   └── index.yaml
└── uploads/           # Images and files (see below)
```

See [Architecture](/reference/architecture) for the underlying data model.

## Uploads

Files dropped into `sites/my-site/uploads/` are automatically imported into the CMS as `site_uploads` records:

```
sites/my-site/uploads/
├── hero.jpg
└── logo.svg
```

- On import, new files become uploads with stable IDs.
- Hash comparison skips re-upload when content is unchanged.
- A file removed from `uploads/` becomes an orphan upload warning — clean it up in the CMS or remove the record from the file system to delete it.

This means you can drop an image into `uploads/` and reference it from an image field without ever opening the CMS.

## site.yaml

`site.yaml` holds the site's name, its `site_id`, and its group:

```yaml
name: My Site
site_id: b0491u6f53g0np3
group: default
```

`site_id` ties the folder to its record in the CMS. Primo writes it for you, so don't edit or copy it by hand.

The site's hostname is **not** stored in files. It's per-environment (a `*.localhost` host in dev, your domain in production) and is set in the dashboard, so `primo push` can't point your production site at `localhost`.

<Warning>
Keep backup copies of a site **outside** `sites/` (for example in a `_backups/` folder at the workspace root). A copy inside `sites/` has the same `site_id`: `primo dev` skips it, and `primo push` refuses to push both.
</Warning>

## Adding Sites

`primo new <name>` creates a site folder under `sites/`, and `primo dev` imports it into the CMS. In an interactive terminal, `primo new` starts the CMS for you; with `--skip-dev`, or from a script, it only creates the files:

```
My Site was created. Start the local CMS to import it:
  primo dev
```

A folder you create by hand (or copy) under `sites/` isn't in the CMS until you register it with `primo add`:

```bash
primo add my-other-site
```

`primo add` needs the workspace's port, so **stop `primo dev` first**, then start it again afterwards. If `primo dev` is running, `primo add` stops and tells you so rather than racing it. Record ids copied from another site are stripped, so a copied folder becomes a new site instead of overwriting the original.

`primo status` lists any folders on disk that aren't registered yet:

```
  1 site on disk but not registered in the CMS:
    ! other  run `primo add other`
```

## Shared Library

The workspace's `library/` folder holds blocks shared across sites. `library/groups.yaml` lists the library's groups and their folders:

```yaml
- name: Shared
  folder: shared
```

Each block lives in `library/<group-folder>/<block>/`, with the same files as a site block. `primo dev` loads the library into the CMS, where editors add library blocks to a site from the block picker. To use a library block on a site in files, copy its folder into `sites/<name>/blocks/` (leaving out its `_id`). The copy is independent afterwards.

## Working with AI Agents

`primo init`, `primo new`, and `primo pull` write an `AGENTS.md` at the workspace root: a guide to the workspace layout, commands, content-design defaults, and valid field types. Most coding agents read it automatically. They also write a `CLAUDE.md` that imports it (`@AGENTS.md`) for Claude Code.

For validation and scaffolding tools, connect the [Primo MCP server](/reference/mcp-server). `primo dev` also registers it in the workspace's `.mcp.json`.

## Site Groups

Groups organize sites in the dashboard (Home Services, Food & Hospitality, and so on). Declare them in the workspace's `server.yaml`, giving each a local `id` and a display `name`:

```yaml
site_groups:
  - id: home-services
    name: Home Services
    index: 0
```

Reference a group from a site's `site.yaml` by that local `id`:

```yaml
name: Goodweather Heating & Air
group: home-services
```

<Warning>
**Use the local `id` in `site.yaml.group`; the `name` is only the display label.** The CLI resolves the id against `server.yaml`, then sends the matching **name** to the server, which assigns its own group id on import and matches groups by name. So the local `id` is a reference the server replaces, and a `site.yaml` that names a group by its display name may not select the one you meant — a typo quietly creates a new group instead.

Expect the server-assigned id to differ from your local id after the first import. `primo dev` and `primo add` print a notice when a configured id looks locally-chosen.
</Warning>

## Avatar Uploads

iPhone HEIC photos are automatically converted to JPEG when uploaded as avatars — no manual conversion required.

## Validating Your Work

Run `primo validate` from the workspace root to check every site, or from a site folder to check just that site:

```bash
primo validate
primo validate -d sites/my-site
```

It catches structural mistakes such as a missing homepage (`pages/index.yaml`), or `fields:` under a `repeater` or `group` field, where nested fields must be listed under `subfields:`.

To rebuild a site's preview while `primo dev` is running, pass the site folder:

```bash
primo preview --dir sites/my-site
```

For AI-assisted development, the [MCP server](/reference/mcp-server) exposes per-file validators (`validate_block`, `validate_page`, `validate_site`) that agents call automatically.
